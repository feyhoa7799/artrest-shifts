# Перенос Supabase в российский контур

Дата аудита: 9 октября 2026 года.

Статус документа: план. Никакие изменения production этим документом не выполняются.

## Цель

Перенести PostgreSQL, Supabase Auth и REST API проекта «Подработка Арт Рест» с managed Supabase на текущий сервер Timeweb Cloud в России, сохранив работу регистрации, входа, профилей, слотов, откликов и админки.

Переход должен быть обратимым. До финального технического окна managed Supabase остаётся основной системой.

## Результаты текущего аудита

Сервер:

- провайдер: Timeweb Cloud;
- дата-центр: Москва, Россия; подтверждено информационным письмом Timeweb;
- текущая стоимость: 3 680 ₽/месяц;
- ОС: Ubuntu 24.04 LTS;
- CPU: 8 vCPU;
- RAM: 12 ГБ, доступно около 10 ГБ;
- swap: 4 ГБ, не используется;
- диск: 100 ГБ NVMe, свободно около 70 ГБ;
- Docker: около 18 ГБ, включая 12,5 ГБ build cache;
- средняя нагрузка во время аудита: менее 0,1 CPU;
- работающие проекты: Подработка, Бонусы, Assessment, Telegram-бот, SSM Event и sing-box;
- мониторинг: установлен Zabbix Agent;
- внешнего backup для общей базы в ходе аудита не обнаружено.

Текущая база Supabase небольшая:

- restaurants: 126;
- slots: 373;
- applications: 32;
- employee_profiles: 222;
- admin_users: 88;
- admin_access_audit: 107;
- admin_restaurant_access: 82;
- user_activity_summary: 198.

Код использует:

- Supabase Auth;
- PostgreSQL через Supabase REST/PostgREST;
- service role в серверных API.

Код не использует Supabase Storage, Realtime и RPC. Эти компоненты не входят в обязательный первый контур.

Текущий managed Supabase:

- регион: West EU, Ирландия (`eu-west-1`);
- PostgreSQL: 17.6;
- целевой self-hosted PostgreSQL: официальный Supabase Postgres 17;
- базовый pinned image для теста: `supabase/postgres:17.6.1.136`.

## Решение

На первом этапе используем текущий сервер. Новый сервер и увеличение тарифа заранее не покупаем.

Целевая схема:

```text
Internet
  -> nginx :443
     -> artrest-shifts-app
     -> Supabase API gateway (только Auth и REST)

Docker internal network
  -> Supabase Auth
  -> PostgREST
  -> PostgreSQL

Private/admin access only
  -> database administration
  -> Supabase Studio, если оно понадобится

Encrypted off-host backup
  -> российское S3 или корпоративное хранилище
```

Ограничения безопасности:

- PostgreSQL не публикуется в интернет;
- административные интерфейсы доступны только через VPN/SSH tunnel;
- наружу публикуются только HTTPS endpoints, нужные сайту;
- используются отдельные Docker network и volumes;
- ключи и пароли не хранятся в Git;
- production secrets не выводятся в команды, логи и отчёты;
- anon остаётся закрыт RLS-политиками;
- service role используется только серверным приложением;
- контейнеры получают healthcheck и ограничения логов.

## Ресурсы и стоимость

### Вариант A: минимальный, выбран для пилота

- текущий сервер 8 vCPU / 12 ГБ / 100 ГБ;
- внешнее холодное S3 для зашифрованных backup: около 1,1 ₽/ГБ в месяц
  по текущему поресурсному тарифу, минимум 1 ГБ;
- дополнительные расходы на сервер: 0 ₽/месяц;
- общий дополнительный бюджет на старте: ориентировочно 1–10 ₽/месяц при
  фактическом объёме до 10 ГБ плюс исходящий трафик при восстановлении.

Точная цена и российская локация S3 проверяются в панели до заказа.

### Вариант B: рекомендуемый запас после нагрузочного наблюдения

- сервер 8 vCPU / 16 ГБ / 160 ГБ;
- фактическая цена в панели Timeweb: 13 600 ₽/месяц;
- текущая стоимость: 3 680 ₽/месяц;
- увеличение: 9 920 ₽/месяц;
- холодное S3 backup: по фактическому объёму; около 110 ₽/месяц даже при
  достижении 100 ГБ. Стандартный фиксированный тариф 100 ГБ стоит около
  349 ₽/месяц и для ежедневного архива сейчас не требуется.

Этот вариант отклонён как экономически нецелесообразный. При нехватке ресурсов сначала рассматриваются дополнительный диск, оптимизация Docker и отдельный недорогой узел базы, а не переход на тариф за 13 600 ₽/месяц.

Переход на этот вариант нужен, если после тестового запуска:

- доступная RAM опускается ниже 3 ГБ;
- диск заполняется более чем на 65–70%;
- появляются устойчивые задержки PostgreSQL или OOM;
- на сервер переносятся Бонусы/Assessment или новые сервисы с общей Auth.

Цены являются ориентиром на дату документа. Фактическую сумму подтверждает личный кабинет Timeweb; смена тарифа вызывает перезагрузку сервера.

## Этапы

### Этап 0. Подтверждение инфраструктуры

Ручные проверки владельца аккаунта:

1. В Timeweb открыть сервер `7159549-sj988628.twc1.net`.
2. Локация дата-центра подтверждена: Москва, Россия.
3. Текущая ежемесячная стоимость подтверждена: 3 680 ₽.
4. Тариф 8 vCPU / 16 ГБ / 160 ГБ стоит 13 600 ₽ и не применяется.
5. В разделе S3 проверить российскую локацию и цену приватного холодного
   bucket с поресурсной тарификацией. Пока не заказывать.
6. Регион managed Supabase подтверждён: Ирландия (`eu-west-1`).
7. Версия PostgreSQL подтверждена: 17.6.

STOP, если сервер или резервное хранилище физически находятся вне РФ.

### Этап 1. Подготовка тестового контура

В отдельной ветке готовятся:

- pinned версии Docker images;
- Compose-файл с Auth, PostgREST и PostgreSQL;
- шаблон переменных без значений;
- healthchecks;
- nginx-конфигурация-шаблон;
- скрипты backup, restore и post-restore validation;
- runbook запуска и rollback.

На production ничего не запускается без отдельного GO.

### Этап 2. Параллельный тест на сервере

После отдельного GO:

1. Создать encrypted backup managed Supabase.
2. Запустить локальный контур на localhost/закрытой Docker network.
3. Не менять текущие переменные приложения.
4. Восстановить копию схем `auth`, `public` и необходимых служебных схем.
5. Проверить число пользователей и строк по ключевым таблицам.
6. Создать отдельную тестовую сборку приложения на другом локальном порту.
7. Проверить регистрацию, вход, сброс пароля, профиль, слоты, отклики, роли, activity tracking и email.

Копия содержит реальные персональные данные и должна иметь тот же режим защиты, что production.

### Этап 3. Backup и мониторинг

До переключения обязательны:

- ежедневный encrypted backup PostgreSQL вне сервера;
- хранение минимум 14 ежедневных, 8 недельных и 12 месячных копий;
- отдельная копия ролей и Auth schema;
- автоматическая проверка завершения backup;
- тестовое восстановление;
- алерты по RAM, диску, PostgreSQL, Auth и API;
- журнал административных действий;
- ограничение и ротация Docker logs.

Backup на том же диске считается только временной копией, но не полноценным резервированием.

### Этап 4. Техническое окно

Переключение выполняется только после отдельного GO:

1. Зафиксировать rollback commit и текущие env checksums без вывода значений.
2. Ограничить записи на короткое техническое окно.
3. Сделать финальный dump managed Supabase.
4. Восстановить локальную базу.
5. Сверить число Auth users и строк ключевых таблиц.
6. Обновить только Supabase URL и ключи приложения.
7. Пересобрать и перезапустить только `artrest-shifts-app`.
8. Выполнить автоматический и ручной smoke-test.
9. Оставить managed Supabase доступным для rollback, но исключить расхождение записей.

Из-за смены JWT пользователям может потребоваться повторный вход. Существующие пользователи и password hashes должны переноситься вместе с Auth schema; это заранее проверяется на тестовом восстановлении.

### Этап 5. Наблюдение и отключение managed Supabase

- наблюдение не менее 7–14 дней;
- ежедневная проверка backup;
- контроль ошибок Auth/API и производительности;
- managed Supabase отключается только после подтверждённого восстановления backup и окончания периода наблюдения.

## Критерии GO

- дата-центр и backup находятся в РФ;
- тестовое восстановление прошло;
- Auth users и контрольные counts совпадают;
- регистрация, login и reset password работают;
- RLS/доступы проверены anon и service role;
- SMTP работает;
- backup ушёл на другой физический носитель;
- выполнено тестовое восстановление;
- есть rollback-план и техническое окно.

## Критерии STOP

- не подтверждена российская локация;
- нет внешнего backup;
- Auth users или таблицы восстановились не полностью;
- неизвестна совместимость версий PostgreSQL;
- anon получает доступ к закрытым таблицам;
- SMTP/reset password не работает;
- доступная RAM менее 3 ГБ или диск заполнен более чем на 70%;
- нет возможности быстро вернуть старые Supabase URL/keys и предыдущий app container.

## Ручные действия пользователя

На текущем этапе ничего покупать и переключать не нужно.

Исходные данные получены. Следующее ручное действие потребуется перед настройкой внешнего backup:

1. В Timeweb открыть «Объектное хранилище S3».
2. Убедиться, что bucket будет размещён в России.
3. Зафиксировать поресурсную цену холодного класса и цену исходящего трафика.
4. Ничего не заказывать до отдельного шага настройки backup.

Теперь можно подготовить Compose и restore-процедуру для PostgreSQL 17.6.
